How the Web Works

Understanding the journey from typing a URL to seeing a webpage

🌍 The Complete Request Flow

When you type www.netflix.com and press Enter, here's what happens:

🎬 Interactive Simulation
1. URL Parsing
Browser breaks down the URL into protocol (https), domain (netflix.com), and path (/browse)
2. DNS Lookup
Converts domain name to IP address (like finding a phone number in a directory)
3. TCP Connection
Establishes connection with server using 3-way handshake (SYN, SYN-ACK, ACK)
4. HTTP Request
Browser sends request for webpage and resources (HTML, CSS, JS, images)
5. Server Processing
Server processes request, queries database if needed, generates response
6. Rendering
Browser parses HTML, constructs DOM, applies CSS, executes JavaScript, renders page
🌟 Real-World Example: YouTube Video Load

When you click a YouTube video:

  1. DNS resolves www.youtube.com to IP (like 142.250.185.46)
  2. Browser requests HTML page via HTTPS
  3. Server sends HTML with video player code
  4. Browser requests video file in chunks (adaptive streaming)
  5. CDN (Content Delivery Network) serves video from nearest server
  6. Buffer fills, video starts playing

Why videos load in chunks? So you don't wait for the entire 2GB file to download before watching!

💼 Interview Tips
  • Q: What happens when you type google.com and press Enter?
    A: Walk through DNS lookup → TCP handshake → HTTP request → Server response → Browser rendering. Mention caching at each step.
  • Q: Difference between client-side and server-side rendering?
    A: Client-side (React, Vue): Server sends minimal HTML + JS, browser builds page. Server-side (Next.js, PHP): Server sends complete HTML, faster initial load.
  • Q: What is a CDN and why use it?
    A: Content Delivery Network distributes content across global servers. User gets content from nearest server → faster load times. Example: Netflix uses AWS CloudFront.
  • Follow-up: What gets cached where?
    A: DNS in OS/browser, static files (images/CSS/JS) in browser cache, API responses in memory/localStorage, entire pages in service workers (PWA).

🎨 Critical Rendering Path

The sequence of steps browser takes to convert HTML/CSS/JS into pixels on screen:

🔄 Rendering Pipeline

Step-by-Step Breakdown:

  1. DOM Construction: HTML → Document Object Model (tree structure)
  2. CSSOM Construction: CSS → CSS Object Model (styling rules)
  3. Render Tree: Combine DOM + CSSOM (only visible elements)
  4. Layout: Calculate exact position & size of each element
  5. Paint: Fill in pixels, text, colors, images, borders, shadows
  6. Composite: Layer management, GPU acceleration for animations
🌟 Real-World: Why Facebook/Instagram Feel Fast

Techniques used:

  • Code Splitting: Load only what's needed (not entire app at once)
  • Lazy Loading: Images load as you scroll (not all upfront)
  • Service Workers: Cache resources, work offline
  • Skeleton Screens: Show placeholder while content loads (better UX than spinners)
  • Prefetching: Predict next page you'll visit, load in background

💼 Interview Tips
  • Q: What is the DOM?
    A: Document Object Model - tree representation of HTML. Browser creates it by parsing HTML. JavaScript can manipulate it to change page content dynamically.
  • Q: Difference between localStorage and sessionStorage?
    A: Both store key-value pairs in browser. localStorage persists even after browser closes (no expiry). sessionStorage clears when tab closes.
  • Q: What causes reflow and repaint?
    A: Reflow: changing layout (width, height, position) - expensive! Repaint: changing colors, backgrounds - cheaper. Minimize by batching DOM changes, using CSS transforms instead of layout properties.
  • Q: How do browsers handle same-origin policy?
    A: Security feature - scripts from one origin (domain + protocol + port) can't access data from another. CORS (Cross-Origin Resource Sharing) headers allow controlled access. Example: fetch() to different domain needs CORS.

🌟 Real-World: How Cloudflare Speeds Up Websites

Without Cloudflare:

User in Bangladesh → DNS query to US server (200ms) → IP returned → Connect to origin server in US (300ms)

With Cloudflare DNS (1.1.1.1):

User in Bangladesh → Cloudflare's Dhaka DNS server (10ms) → Cached IP returned instantly → Connect to nearest Cloudflare edge (20ms)

Result: 500ms+ saved on every request! That's why sites using Cloudflare feel faster.

Try it: Change your DNS to 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google) - noticeable speed boost!

💼 Interview Tips
  • Q: What is DNS and why is it needed?
    A: DNS translates domain names to IP addresses. Needed because humans remember names (google.com) better than IPs (142.250.185.46). It's distributed, hierarchical system with caching at multiple levels.
  • Q: Explain DNS resolution process step-by-step.
    A: Browser cache → OS cache → Router cache → ISP resolver → Root server (.com) → TLD server → Authoritative nameserver → IP returned. Caching at each level speeds up future requests.
  • Q: What is DNS propagation?
    A: When you change DNS records, it takes time (up to 48 hours) to update globally due to TTL (Time To Live) caching. Lower TTL = faster propagation but more DNS queries.
  • Q: Difference between DNS and CDN?
    A: DNS resolves domain to IP. CDN (Content Delivery Network) caches actual content (images, CSS, JS) on edge servers globally. DNS can route to nearest CDN server using GeoDNS.

⚡ DNS Performance Tips

Use Fast DNS Providers
Cloudflare (1.1.1.1), Google (8.8.8.8) are faster than default ISP DNS
DNS Prefetching
<link rel="dns-prefetch" href="//api.example.com"> - resolve DNS before actually needed
Reduce DNS Lookups
Each unique domain requires DNS lookup. Minimize third-party domains (analytics, fonts, ads)
Set Appropriate TTL
Higher TTL = better caching but slower updates. Lower TTL = faster changes but more queries

HTTP & HTTPS

The protocol that powers the web - communication rules between client and server

📡 HTTP (HyperText Transfer Protocol)

HTTP is a stateless, request-response protocol. Each request is independent - server doesn't remember previous requests (unless using cookies/sessions).

📨 HTTP Request/Response Anatomy

HTTP Request

GET /api/users/123 HTTP/1.1 Host: api.example.com User-Agent: Mozilla/5.0 (Windows NT 10.0) Accept: application/json Authorization: Bearer eyJhbGc... Cookie: session_id=abc123 // Request Body (for POST/PUT) { "name": "John Doe", "email": "john@example.com" }

HTTP Response

HTTP/1.1 200 OK Content-Type: application/json Content-Length: 156 Cache-Control: max-age=3600 Set-Cookie: session_id=xyz789; HttpOnly Server: nginx/1.18.0 // Response Body { "id": 123, "name": "John Doe", "email": "john@example.com" }

HTTP Methods (Verbs):

Method Purpose Idempotent? Example
GET Retrieve data (read only) Yes Get user profile, fetch products
POST Create new resource No Create user, submit form, upload file
PUT Update/replace entire resource Yes Update user profile completely
PATCH Partial update Maybe Update only email field
DELETE Remove resource Yes Delete user account, remove post
HEAD Same as GET but no body Yes Check if resource exists, get metadata
OPTIONS Get allowed methods Yes CORS preflight request

Idempotent: Multiple identical requests have same effect as single request. GET /users/1 ten times = same result. POST /users creates 10 users!

📊 HTTP Status Codes

1xx - Informational
100 Continue, 101 Switching Protocols (rare in practice)
2xx - Success
200 OK, 201 Created, 204 No Content
3xx - Redirection
301 Moved Permanently, 302 Found, 304 Not Modified (cache)
4xx - Client Error
400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xx - Server Error
500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable

Common Status Codes Explained:

  • 200 OK - Request successful, here's your data
  • 201 Created - Resource created successfully (POST response)
  • 301 Moved Permanently - Permanent redirect (SEO-friendly)
  • 302 Found - Temporary redirect
  • 304 Not Modified - Use cached version (saves bandwidth!)
  • 400 Bad Request - Malformed request (client error)
  • 401 Unauthorized - Authentication required
  • 403 Forbidden - Authenticated but no permission
  • 404 Not Found - Resource doesn't exist
  • 429 Too Many Requests - Rate limit exceeded
  • 500 Internal Server Error - Server crashed/bug
  • 502 Bad Gateway - Server can't reach backend
  • 503 Service Unavailable - Server overloaded/maintenance

🔒 HTTPS (HTTP Secure)

HTTPS = HTTP + TLS/SSL encryption. Data is encrypted in transit, preventing eavesdropping and tampering.

Encryption
Data encrypted with SSL/TLS. Third parties can't read it even if intercepted
Authentication
SSL certificate proves server identity (prevents phishing)
Data Integrity
Detects if data was modified in transit
SEO Boost
Google ranks HTTPS sites higher than HTTP

SSL/TLS Handshake Process:

  1. Client sends "Client Hello" with supported cipher suites
  2. Server responds with "Server Hello" + SSL certificate
  3. Client verifies certificate with Certificate Authority (CA)
  4. Client generates session key, encrypts with server's public key
  5. Server decrypts with private key
  6. Both use session key for symmetric encryption (faster than asymmetric)
  7. Secure connection established! 🎉
🌟 Real-World: Facebook Login Flow

Step-by-step HTTP requests when you log into Facebook:

  1. GET facebook.com → Receives login page HTML
  2. GET /assets/styles.css → Downloads CSS files
  3. GET /assets/scripts.js → Downloads JavaScript
  4. POST /login → Sends email + password (HTTPS encrypted!)
  5. Server validates → Checks credentials against database
  6. Response: 302 Redirect → Set-Cookie: session_token=xxx
  7. GET /home → Cookie sent automatically in request header
  8. Server validates session → Returns your feed

Why HTTPS matters here: Without it, someone on same WiFi could steal your password or session cookie!

💼 Interview Tips
  • Q: Difference between HTTP and HTTPS?
    A: HTTPS encrypts data with SSL/TLS. HTTP sends plain text - anyone can read it. HTTPS also authenticates server identity with certificates. All modern sites should use HTTPS.
  • Q: What happens in an HTTP request?
    A: Client sends request with method (GET/POST), headers (auth, cookies), optional body. Server processes, sends response with status code, headers, body. Connection may be kept alive (HTTP/1.1+) or closed.
  • Q: Difference between GET and POST?
    A: GET retrieves data, parameters in URL, cacheable, idempotent, no body. POST sends data in body, not cacheable, not idempotent, can have large payload. Use GET for reading, POST for creating.
  • Q: What is CORS and why needed?
    A: Cross-Origin Resource Sharing. Browser security prevents JS on domain A from accessing domain B's API. CORS headers (Access-Control-Allow-Origin) allow controlled access. Prevents malicious sites from stealing data.
  • Q: Explain HTTP caching.
    A: Cache-Control header controls caching. max-age=3600 caches for 1 hour. ETag/If-None-Match for validation. 304 Not Modified saves bandwidth. Browser/proxy/CDN can cache. Reduces server load, faster load times.

🆕 HTTP Versions

Version Year Key Features Limitations
HTTP/1.0 1996 Basic request/response, methods, headers New connection per request (slow!)
HTTP/1.1 1997 Persistent connections, pipelining, chunked transfer Head-of-line blocking, text-based
HTTP/2 2015 Multiplexing, binary protocol, server push, header compression Still TCP-based (latency in poor networks)
HTTP/3 2022 QUIC (UDP-based), faster handshake, better mobile Newer, not universally supported yet

Real impact: HTTP/2 can load 100 resources in 1 connection vs HTTP/1.1 needing 6+ connections. Google, Facebook, Netflix all use HTTP/2+.
