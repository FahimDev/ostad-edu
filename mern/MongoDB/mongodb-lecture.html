Core Principles of MongoDB Schema Design

The Three Questions Framework

Before designing any collection, ask yourself these three questions:

1. How is this data queried?

If you always need data together → embed

Example: Product with its specifications

2. Does this grow unbounded?

If it can grow infinitely → reference

Example: Product reviews (could be 10 or 10,000)

3. Is this needed in multiple places?

Shared across many docs → reference

Specific to one doc → embed

Embedding vs Referencing

Use Case Embed Reference Reason
Product → Brand ✗ ✓ Many products share one brand
Product → Specifications ✓ ✗ Always queried together, bounded size
Product → Reviews ✗ ✓ Unbounded growth (could be thousands)
User → Profile ✓ ✗ 1:1 relationship, queried together
User → Orders ✗ ✓ Grows over time, queried separately
Order → Order Items ✓ ✗ Bounded, immutable after creation
⚠️ Common Mistake: Don't apply SQL normalization rules to MongoDB! It's okay to denormalize data. A little redundancy can save you from complex $lookup operations.

Simple Reference Collections

Brand Collection

Brands are shared across many products. Simple reference collection.

// brands collection { "_id": ObjectId("507f1f77bcf86cd799439011"), "name": "Apple", "slug": "apple", "logo": "https://cdn.example.com/apple-logo.png", "description": "Technology company", "isActive": true, "createdAt": ISODate("2024-01-15T10:30:00Z"), "updatedAt": ISODate("2024-01-15T10:30:00Z") }

Category Collection

Categories organize products. Can support nested categories with parent reference.

// categories collection { "_id": ObjectId("507f1f77bcf86cd799439012"), "name": "Smartphones", "slug": "smartphones", "parentId": ObjectId("507f1f77bcf86cd799439010"), // ref to "Electronics" "image": "https://cdn.example.com/smartphones.jpg", "description": "Mobile phones and accessories", "order": 1, // for display ordering "isActive": true, "createdAt": ISODate("2024-01-15T10:30:00Z"), "updatedAt": ISODate("2024-01-15T10:30:00Z") }
Design Decision: We use references for brands and categories because:
  • Multiple products share the same brand/category
  • Brand/category info might be updated centrally
  • We can query products by brand/category efficiently with indexes

Product Collection - The Heart of E-commerce

Products are the most complex collection. Let's build it step by step.

Critical Question: What to Embed vs Reference?

// products collection { "_id": ObjectId("507f1f77bcf86cd799439013"), "name": "iPhone 15 Pro", "slug": "iphone-15-pro", "sku": "APPL-IPH15P-256-BLK", // REFERENCE: Shared entities "brandId": ObjectId("507f1f77bcf86cd799439011"), "categoryId": ObjectId("507f1f77bcf86cd799439012"), // EMBED: Product-specific data always needed together "description": "Latest flagship smartphone...", "shortDescription": "6.1-inch Super Retina XDR display", "pricing": { "regularPrice": 999.99, "salePrice": 949.99, "currency": "USD", "discount": 5 // percentage }, "inventory": { "stock": 150, "reserved": 5, // in pending carts "available": 145, "lowStockThreshold": 10 }, // EMBED: Bounded array, always displayed "images": [ { "url": "https://cdn.example.com/iphone-main.jpg", "alt": "iPhone 15 Pro front view", "isPrimary": true, "order": 1 }, { "url": "https://cdn.example.com/iphone-back.jpg", "alt": "iPhone 15 Pro back view", "isPrimary": false, "order": 2 } ], // EMBED: Product specs (bounded, queried together) "specifications": { "screen": "6.1-inch OLED", "processor": "A17 Pro chip", "storage": "256GB", "ram": "8GB", "battery": "3274 mAh", "weight": "187g" }, // Ratings summary (denormalized for performance) "ratings": { "average": 4.5, "count": 328 }, "isActive": true, "isFeatured": true, "tags": ["smartphone", "5G", "flagship"], "createdAt": ISODate("2024-01-15T10:30:00Z"), "updatedAt": ISODate("2024-01-15T10:30:00Z") }
✓ Best Practice: Denormalize ratings
We store average rating and count directly in the product document even though reviews are in a separate collection. Why? This data is displayed on every product card. Computing it with aggregation for every product list would be too slow.
✗ Anti-pattern: DON'T embed reviews
Never embed reviews as an array in the product document. A popular product could have thousands of reviews, making the document huge and slow to query. Always use a separate reviews collection with productId reference.

User, Profile, Wishlist & Cart

User Collection

Core user authentication and profile data. Profile is embedded because it's always needed together and bounded in size.

// users collection { "_id": ObjectId("507f1f77bcf86cd799439014"), "email": "john.doe@example.com", "passwordHash": "$2b$10$...", // bcrypt hash "role": "customer", // customer, admin, vendor // EMBED: Profile (1:1, always queried together) "profile": { "firstName": "John", "lastName": "Doe", "phone": "+1-555-0123", "avatar": "https://cdn.example.com/avatars/user123.jpg", "dateOfBirth": ISODate("1990-05-15T00:00:00Z"), "gender": "male" }, // EMBED: Addresses (bounded, max 5-10 typically) "addresses": [ { "_id": ObjectId("507f1f77bcf86cd799439020"), "type": "home", "street": "123 Main St", "city": "New York", "state": "NY", "zip": "10001", "country": "USA", "isDefault": true } ], // EMBED: Wishlist (product IDs, usually < 100 items) "wishlist": [ { "productId": ObjectId("507f1f77bcf86cd799439013"), "addedAt": ISODate("2024-01-20T14:30:00Z") } ], "isEmailVerified": true, "isActive": true, "lastLogin": ISODate("2024-01-25T09:15:00Z"), "createdAt": ISODate("2024-01-10T08:00:00Z"), "updatedAt": ISODate("2024-01-25T09:15:00Z") }

Cart Collection (Separate)

Carts are temporary and modified frequently. Separate collection prevents constant updates to the user document.

// carts collection { "_id": ObjectId("507f1f77bcf86cd799439015"), "userId": ObjectId("507f1f77bcf86cd799439014"), // CRITICAL: Snapshot price at add-to-cart time! "items": [ { "productId": ObjectId("507f1f77bcf86cd799439013"), "quantity": 2, "priceAtAdd": 949.99, // snapshot for cart total "addedAt": ISODate("2024-01-25T10:00:00Z") } ], "subtotal": 1899.98, "discountAmount": 0, "total": 1899.98, "expiresAt": ISODate("2024-01-26T10:00:00Z"), // auto-delete old carts "updatedAt": ISODate("2024-01-25T10:00:00Z") }
Why separate cart collection?
  • Carts are modified frequently (add, remove, update quantity)
  • Not every user has an active cart
  • Easy to expire/delete abandoned carts with TTL index
  • Prevents bloating the user document
✓ Price Snapshotting is CRITICAL!
Always snapshot the price when a product is added to cart. Product prices change, but cart totals should remain stable until checkout. During checkout, validate against current price and warn user if it changed.

Review Collection

Reviews are in a separate collection because they grow unbounded and are not always needed when viewing products.

// reviews collection { "_id": ObjectId("507f1f77bcf86cd799439016"), "productId": ObjectId("507f1f77bcf86cd799439013"), "userId": ObjectId("507f1f77bcf86cd799439014"), "rating": 5, // 1-5 stars "title": "Amazing phone!", "comment": "Best smartphone I've ever owned...", // Denormalize user info for display (avoid joins) "userName": "John Doe", "userAvatar": "https://cdn.example.com/avatars/user123.jpg", // Images (optional, bounded) "images": [ "https://cdn.example.com/reviews/img1.jpg" ], "verifiedPurchase": true, "helpfulCount": 12, // users who found it helpful "isApproved": true, "createdAt": ISODate("2024-01-22T15:30:00Z") }
✓ Denormalization Strategy:
We store userName and userAvatar directly in the review, even though it duplicates data from the users collection. This avoids expensive $lookup joins when displaying reviews. User display info rarely changes.

Updating Product Rating (Background Job)

// Aggregation to recalculate product ratings db.reviews.aggregate([ { $match: { productId: ObjectId("507f1f77bcf86cd799439013") } }, { $group: { _id: "$productId", avgRating: { $avg: "$rating" }, count: { $sum: 1 } } } ]) // Then update the product document db.products.updateOne( { _id: ObjectId("507f1f77bcf86cd799439013") }, { $set: { "ratings.average": 4.5, "ratings.count": 328 } } )

Invoice, Invoice Products & Payment

Invoice Collection

Invoices are immutable records. We embed order items because they never change after order creation.

// invoices collection { "_id": ObjectId("507f1f77bcf86cd799439017"), "invoiceNumber": "INV-2024-00123", "userId": ObjectId("507f1f77bcf86cd799439014"), // EMBED: Invoice items (immutable after creation) "items": [ { "productId": ObjectId("507f1f77bcf86cd799439013"), "productName": "iPhone 15 Pro", // snapshot "sku": "APPL-IPH15P-256-BLK", "quantity": 2, "unitPrice": 949.99, "totalPrice": 1899.98, "image": "https://cdn.example.com/iphone-main.jpg" } ], // EMBED: Shipping address snapshot "shippingAddress": { "street": "123 Main St", "city": "New York", "state": "NY", "zip": "10001", "country": "USA" }, "subtotal": 1899.98, "tax": 151.99, "shippingCost": 15.00, "discount": 0, "total": 2066.97, "currency": "USD", "status": "paid", // pending, paid, shipped, delivered, cancelled "paymentId": ObjectId("507f1f77bcf86cd799439018"), "createdAt": ISODate("2024-01-25T11:00:00Z"), "updatedAt": ISODate("2024-01-25T11:05:00Z") }

Payment Collection

// payments collection { "_id": ObjectId("507f1f77bcf86cd799439018"), "invoiceId": ObjectId("507f1f77bcf86cd799439017"), "userId": ObjectId("507f1f77bcf86cd799439014"), "amount": 2066.97, "currency": "USD", "method": "stripe", // stripe, paypal, razorpay, etc. "status": "completed", // pending, completed, failed, refunded // Gateway-specific details "gatewayResponse": { "transactionId": "ch_3OYxyz123456789", "paymentIntentId": "pi_3OYxyz987654321", "receiptUrl": "https://stripe.com/receipt/xyz" }, "createdAt": ISODate("2024-01-25T11:02:00Z"), "completedAt": ISODate("2024-01-25T11:05:00Z") }
✓ Critical: Snapshot Everything!
Notice how we embed product names, prices, and shipping addresses in the invoice? This is crucial! Products might be deleted, prices change, addresses updated — but invoices must remain accurate historical records. Always snapshot data at the moment of purchase.

Golden Rules for Payment Integration

1. Never Trust Client Side

Always verify payment on your server, not the frontend. Clients can be manipulated.

2. Use Webhooks

Payment gateways send webhooks for status updates. Always implement webhook handlers.

3. Idempotency Keys

Prevent duplicate charges by using unique idempotency keys for each transaction.

4. Store Gateway IDs

Always save transaction IDs, payment intent IDs from the gateway for reconciliation.

5. Handle All States

Payments can be: pending, succeeded, failed, refunded, disputed. Handle all cases.

6. Security First

Never log or store full card numbers. Use gateway's tokenization. Follow PCI compliance.

Common Payment Gateways

  • Stripe: Most developer-friendly, great documentation, international support
  • PayPal: High user trust, widely recognized, easy checkout
  • Razorpay: Popular in India, UPI support, comprehensive features
  • SSLCommerz: Bangladesh-specific, local payment method support (bKash, Nagad, Rocket)
  • Square: Good for retail + online integration

Critical: Verify Payment Before Fulfillment

// Example workflow (pseudo-code) // 1. Create payment intent on your server const paymentIntent = await stripe.paymentIntents.create({ amount: 206697, // in cents currency: 'usd', metadata: { orderId: invoice._id.toString() } }); // 2. Save payment record in MongoDB (status: pending) await db.payments.insertOne({ invoiceId: invoice._id, amount: 2066.97, status: 'pending', gatewayResponse: { paymentIntentId: paymentIntent.id } }); // 3. Webhook handler receives confirmation app.post('/webhook/stripe', async (req, res) => { const sig = req.headers['stripe-signature']; const event = stripe.webhooks.constructEvent(req.body, sig, webhookSecret); if (event.type === 'payment_intent.succeeded') { // Update payment status await db.payments.updateOne( { 'gatewayResponse.paymentIntentId': event.data.object.id }, { $set: { status: 'completed', completedAt: new Date() } } ); // Update invoice status await db.invoices.updateOne( { paymentId: payment._id }, { $set: { status: 'paid' } } ); // Reduce inventory, send confirmation email, etc. } res.json({ received: true }); });
⚠️ NEVER Do This:
  • Store credit card numbers in your database
  • Trust client-side payment success without server verification
  • Forget to validate webhook signatures (security risk!)
  • Start fulfillment before payment is confirmed
  • Ignore failed payment webhooks

Common Anti-patterns to Avoid

1. Embedding Unbounded Arrays

❌ BAD: Embedding all reviews in product document
{ "_id": ObjectId("..."), "name": "iPhone 15 Pro", "reviews": [ // DON'T DO THIS! { /* review 1 */ }, { /* review 2 */ }, // ... could be thousands! ] }
Problem: Document can grow beyond 16MB limit. Slow queries. Can't paginate reviews efficiently.

2. Over-normalization

❌ BAD: Separate collection for product specifications
// products collection { "_id": ObjectId("..."), "name": "iPhone", "specId": ObjectId("...") } // specifications collection (unnecessary!) { "_id": ObjectId("..."), "screen": "6.1 inch", "ram": "8GB" }
Problem: Requires $lookup for every product query. Specs are always needed with product.

3. Not Snapshotting Prices

❌ BAD: Storing only product ID in cart/invoice
// Invoice items without price snapshot "items": [ { "productId": ObjectId("...") } // Missing price! ]
Problem: If product price changes, historical invoices show wrong totals!

4. Massive Document Size

❌ BAD: Storing large binary data in documents
{ "productImage": "data:image/jpeg;base64,/9j/4AAQ..." // MB of base64! }
Problem: Documents should be <16MB. Use GridFS or cloud storage (S3, Cloudinary) for files.

5. No Indexes on Query Fields

❌ BAD: Querying without indexes
// Frequent query without index db.products.find({ categoryId: ObjectId("...") }) // But no index on categoryId!
Problem: Full collection scan on every query. Slow performance.

✓ Solution: Create index: db.products.createIndex({ categoryId: 1 })

Summary & Next Steps

Key Takeaways

🎯 Data Modeling Mindset

Design schemas based on how you query, not how data is structured in theory. MongoDB rewards application-first thinking.

📦 Embed vs Reference

Embed when data is queried together and bounded. Reference when it grows unbounded or is shared across documents.

📸 Snapshot Critical Data

For invoices and orders, snapshot prices, product details, and addresses. Historical records must remain accurate.

⚡ Denormalize for Performance

Don't be afraid of data duplication. Store usernames in reviews, ratings in products. A little redundancy beats expensive joins.

🔐 Payment Security

Never trust client-side payment confirmations. Use webhooks. Store gateway IDs. Never store card numbers.

🚫 Avoid Anti-patterns

No unbounded arrays. No massive documents. Always index query fields. Don't over-normalize.
